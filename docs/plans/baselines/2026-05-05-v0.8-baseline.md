## 3. R6 误报分析（必须修扫描器，不是改 LLM）

R6 当前判定：**段落 ≥4 句 且 段落内不出现 EMOTION_WORDS 或 ROAST_WORDS** → 命中。

ROAST_WORDS 当前：`("反差", "操作", "属于是", "典中典", "整活", "翻车", "拉满", "尴尬到", "降智")`

但 v0.8 输出明显已经有强吐槽视角，只是用了**不同的词**：

| v0.8 句子片段 | 实际带的吐槽词 | 是否在 ROAST_WORDS |
|---|---|---|
| "这教育内容连基本事实都搞错，分明是糊弄小孩和家长" | "糊弄" | ❌ |
| "这种低成本制作，全靠配音硬撑" | "低成本""硬撑" | ❌ |
| "节奏拖沓，成年人看会觉得无聊到爆" | "拖沓""爆" | ❌（"爆"不是"爆棚"） |
| "典型的'说一套做一套'，制作粗糙" | "典型的""粗糙" | ❌（"典型的"≠"典中典"） |
| "这种错误直接摧毁教育视频的 credibility" | "摧毁" | ❌ |
| "这简直是误导，狗明明是'Woof'" | "简直""误导" | ❌ |

**结论**：R6 词典是基于 v0.7 时代的反例归纳的，不覆盖 v0.8 prompt 引导出的新吐槽词系。**这是 P0 修扫描器的问题，不是 LLM 没做对。**

## 5. 数据驱动决策：Stage1/Stage2 是否真要分实现？

### 选项对比

| 选项 | 实施成本 | 预期收益 | 风险 |
|---|---|---|---|
| **B0. 仅修扫描器 + 不动架构**（YAGNI 极致版） | 0.3d（修 R6 词典 + 加 4 个 v0.8 时代吐槽词） | floor check 通过率从 0% → 80%+；当前单人格输出在 75 分档位 | 单一人格"毒舌中年"对治愈题材会冒犯（如儿歌、Vlog） |
| **B1. 加人格选择器（轻量集成）** | 1d（scripting handler 加 1 行 LLM 推断 persona_id → 注入 plot_summary.py 的 user 段落） | 人格按内容自适应，单 LLM call，无架构拆分 | 人格 ≠ Stage1 完整能力（Stage1 还该输出钩子候选 + 段落骨架） |
| **B2. 完整两阶段架构**（debate U6 原方案） | 3-4d（Stage1 独立 LLM call + Stage2 LLM call + 降级链路 + 缓存层 + UI 按钮） | 钩子候选可被用户选择；Stage2 失败优雅降级；目标分 85 | 多 1 次 LLM call ≈ +3s 延迟 + ¥0.001/次；Stage1 输出格式 schema 复杂；端到端调试成本高 |

### 推荐：B0 + B1 渐进路径，跳过 B2

**理由（基于本 baseline 数据）**：

1. **R1/R5 命中率已经从 100%/67% 降到 0** — prompt 层已经解决了 v0.7 的核心问题（百度百科风格），不需要靠架构拆分来解决
2. **R6 是扫描器误报** — 修扫描器（B0）比改 LLM 提示词（B2）便宜一个数量级
3. **当前单人格输出已达 75 分**（人工 review 4/5 通过）— Stage1 单独可交付目标已经达成，B2 是在追求 85 分上限，但 75 分对 MVP 是够的
4. **Stage1/Stage2 分实现 ≠ 必须分两次 LLM call** — 完全可以在单次 LLM call 内用 chain-of-thought 让模型先想钩子候选再写段落，避免 +3s 延迟
5. **Karpathy 准则 §2 简洁优先**：B2 是为"未失败的场景"做的过度防御。Stage2 失败概率多大？当前 0 个失败案例，先收集数据再说

**保留 B2 的触发条件（写进 plan.md，不立即做）**：
- 触发 1：B0+B1 跑 5 部不同题材的视频后，>30% 出现"人格不适配"问题
- 触发 2：用户在 UI 上明确要求"看到多个钩子候选再选"
- 触发 3：Stage2 失败率 >10%（首先得有 Stage2 才能统计）
